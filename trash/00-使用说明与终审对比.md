## 二、每天怎么用（3分钟启动法）

1. 打开当天条目，只做「主任务」1条（45–70min）。
2. 有余力做「加餐」1条（15–30min）。**没余力直接跳过，不算欠债**。
3. 做完立刻在条目末尾打 `[x]`，并写一行「卡点」。
4. 连续 3 天没推进 → 自动降到「最小可执行版」（只做 15min 那条）。

## 四、终审把关：三个模型怎么比才有效

**前提说明**：我（GitHub Copilot）**无法调用** GPT-5.6 Luna 或 doubao 的接口，也不能替它们作答。所以我做的是：

- 我自己产出一份**完整可执行版**（本目录 4 个文件）；
- 给你一份**统一的终审提示词 + 打分表**，你把同一份原始计划分别喂给 GPT-5.6 Luna、doubao，三份输出按同一维度打分，谁赢用谁。

### 4.1 统一终审提示词（原样复制）

```
你是一名资深独立开发者转型顾问。下面是同一个人的半年副业计划。

约束（不可更改）：
- 在职前端，5年全栈，每日仅1-2h，绝不熬夜
- 不裸辞、零主动营销、不接定制外包
- 总试错预算≤1.5w，私有云≤3000
- 目标：标准化数字产品睡后收入 + AI工程能力沉淀

任务：
1. 指出计划中「最可能让它失败」的3个点，按严重程度排序，各给一个可执行的修正动作。
2. 把第1-8周拆到「天」（每天1-2h），每天给出：主任务、产出物、验收标准、1-2个具体资源链接。
3. 明确标出哪些天是「可跳过不影响主线」的。
4. 给出一个「连续失败3天后的降级方案」。

输出要求：Markdown 表格 + 清单，不要空话套话，不要重复我的原话。
```

### 4.2 打分表（三份输出各打一次，满分 5 分）

| 维度 | 说明 | 权重 |
|---|---|---|
| 可执行性 | 今天打开就能干，不用再查 | ×3 |
| 资源真实度 | 链接/命令可直接用，不编造 | ×3 |
| 依赖顺序 | 不会出现「还没装 Docker 就写 Dockerfile」 | ×3 |
| 降级/兜底 | 有减量方案，不制造焦虑 | ×2 |
| 成本意识 | 明确标出哪些要花钱、多少 | ×2 |
| 时间估算可信 | 单日不超 2h | ×2 |
| 原创性 | 不照抄计划原文 | ×1 |

加权总分最高者，用于**最终把关**；另外两家用于**交叉校验**（只吸收它们的差异点）。

### 4.3 我的建议用法

- **排期/拆解**：用本目录（已拆到天，含真实资源）。
- **终审挑错**：用你评分最高那个模型，只跑「原始计划 + 第1条任务（找失败点）」，不重复拆解。
- **不要三家都拆一遍**：浪费 token，且拆解质量差异远小于「执行与否」的差异。

## 五、本拆解相对原计划的 5 处修正

1. **原计划 W1 一天要装完 Docker+Gitea+目录规范** → 拆成 7 天，避免第1天就卡死。
2. **原计划缺少「评测集」环节**，导致 W15 调优无基准 → 在 Day 103 补入 RAG 评测集与 badcase 回归。
3. **原计划 W11 上架未考虑支付回调与自动发货**，是最大变现断点 → Day 73–74 提前锁定。
4. **原计划 W13 SEO 只写文章**，缺 sitemap/收录提交 → Day 90 补齐，否则零流量。
5. **原计划无「降级方案」** → 每个阶段末设置降级线，避免完不成即崩盘。
