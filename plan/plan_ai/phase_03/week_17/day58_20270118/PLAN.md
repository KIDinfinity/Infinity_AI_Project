```markdown
# P3 问题定义 · SP-B 需求 → 任务拆解 → Issue 草案

## 1. 问题

拿到一份需求（PRD/口头需求整理稿）后，手工读需求 → 拆任务 → 估时 → 写验收标准 → 建 Issue，
每次 \_\_ 分钟；常见问题：漏掉非功能需求、验收标准不可测、与历史 issue 重复。

## 2. 用户

- 主用户：自己（在职前端/全栈，每周 \_\_ 个需求）
- 次用户：3–20 人小型研发团队的 Tech Lead / 全栈开发

## 3. 场景

触发：新需求到达 / 迭代计划会前。输入：脱敏需求文本 + 团队规范 KB + 历史 issue。
输出：结构化任务表（标题/描述/估时/验收标准/依赖）→ 人工编辑审批 → Gitea Issue。

## 4. 价值

| 项                 | 手工                    | WorkPilot 目标 |
| ------------------ | ----------------------- | -------------- |
| 单需求耗时         | \_\_ 分钟（Day61 实测） | ≤ 手工的 50%   |
| 验收标准可测试比例 | \_\_ %                  | ≥ 80%          |
| 与历史 issue 重复  | 靠记忆                  | 自动检索提示   |

## 5. 验证方式

离线：20 条场景评测集 + LLM judge + 10 条人审（W20）。
在线：审批前编辑 diff 比例（隐式反馈）、👍/👎、真实使用次数。

## 6. 交付方式

Web 场景页（主）+ MCP 工具 `scenario_spb_run`（辅，P2）+ API。可私有部署（docker compose）。

## 7. 商业模式

开源核心免费；Pro Kit（生产部署包 + 场景包 prompt/rubric/评测集 + 手册）¥199–499 一次性（W22 定价）。

## 8. 技术组合

M1 Gateway（structured）+ M2 检索（规范 KB）+ M6 工具（gitea_issue_read / create）

- M7 LangGraph（interrupt 审批 + checkpoint）+ M3 评测 + M11 认证/隔离/护栏。
```

## 7. 概念自检（不看资料，口述，附答案）

1. 为什么 8 要素里「技术组合」排最后？（答：问题决定技术；先选技术会导致为技术找问题，P3 价值讲不清）

5. 隐式反馈是什么？（答：用户审批前对任务表的编辑行为，编辑越多说明草案越差，不需要用户主动点 👎）
