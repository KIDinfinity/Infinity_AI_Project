# Week 03 · TASKS

## Task 1：建立候选问题池

### 做什么
收集 ≥10 个真实问题/痛点（工作重复劳动、AI 工具痛点、信息整理、自动化需求等）。

### 为什么做
DA-01 必须从真实问题出发，而不是从技术出发。

### 对 DA-01 的贡献
给 DA-01 提供「值得做的问题」来源，避免凭空造产品。

### 前置依赖
无。

### 具体执行步骤
1. 列出工作中反复遇到的问题、开发者常见重复劳动、AI 使用痛点等。
2. 凑满 ≥10 个，每个一句话描述。

### 验收标准
问题池 ≥10 个，来源真实、非臆造。

### 完成后的产出
问题池清单。

### 如果没有必要
必做，不可删除。

---

## Task 2：筛选 3 个候选

### 做什么
从问题池挑 3 个，各写「问题/谁有/何时/现状/改进/付费意愿/最小方案/技术组合」。

### 为什么做
用结构化分析过滤掉「听起来好但没人付费」的伪需求。

### 对 DA-01 的贡献
把问题池收敛成可比较的候选，逼近 DA-01 真身。

### 前置依赖
Task 1。

### 具体执行步骤
对每个候选回答 8 个字段（含技术组合：纯软件/AI/自动化/视觉/物理世界/机器人），写成一页。

### 验收标准
3 个候选各有完整结构化分析，且技术组合判断清晰。

### 完成后的产出
3 份候选分析。

### 如果没有必要
候选不足 3 个时，回到问题池继续补充。

---

## Task 3：确定验证方案

### 做什么
为每个候选设计低成本验证（Landing Page / CLI 原型 / 插件原型 / Agent Demo / 脚本 / 交互原型 / 最小视觉实验 / IoT Demo）。

### 为什么做
用最小成本先验证问题真实存在，避免直接开发 100 小时做错方案。

### 对 DA-01 的贡献
让 DA-01 在写代码前先经过验证，降低方向风险。

### 前置依赖
Task 2。

### 具体执行步骤
为每个候选写一个最小验证方案 + 一个「只给 7 天我能做出什么」；优先用最轻的技术组合验证（能纯软件就不加硬件）。

### 验收标准
每个候选都有可执行的最小验证方案。

### 完成后的产出
候选验证方案。

### 如果没有必要
必做。

---

## Task 4：选出主候选并明确 DA-01

### 做什么
回答「用户是谁/现状/是否频繁/最小方案/技术组合/7 天能做什么」，选出 1 个主候选，写入 DA-01 定义。

### 为什么做
本周必须把 DA-01 从「待定」收敛为「明确方向」，后续所有任务围绕它。

### 对 DA-01 的贡献
正式确定 DA-01 的问题与技术组合，形成唯一主线。

### 前置依赖
Task 2 + Task 3。

### 具体执行步骤
1. 用 5 个问题打分 3 个候选。
2. 选 1 个主候选（或明确「都不成立，继续寻找」）。
3. 明确主候选的技术组合（纯软件/AI/自动化/视觉/物理世界/机器人）。
4. 把主候选的问题/用户/价值/技术组合回填到 PROJECT_CONFIG 的 DA-01 状态。

### 验收标准
有 1 个主候选，且 3 分钟能讲清它解决什么问题、用什么技术组合。

### 完成后的产出
DA-01 候选定义 + PROJECT_CONFIG 回填。

### 如果没有必要
「都不成立，继续寻找」也是有效结果，不算失败。
