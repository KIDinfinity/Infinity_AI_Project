# 截断原因分析

> 结论先行：**几乎可以确定是「单次回复的输出 token 上限」被撞上了**，而不是上下文（输入）满了。

---

## 可能性从高到低

### ① 单次回复「最大输出 token」上限 —— 最可能（~80%）

那条截断的文字是模型在**连续产出**时停在半句：「…Let me make it function」，后面没有任何报错、没有省略号、也没有「（被截断）」提示。

这是「输出 token 上限」的典型指纹：**生成到 cap 那一瞬间，流就硬停**，不会回头补一句「对不起我超了」。原因是产出物本身太长——一次写完 `conftest.py`（三个 fixture）+ 解释设计权衡，思考链里还反复纠结 `tmp_config` 的 scope 和全局状态耦合，输出累计就顶到上限了。

### ② 思考/推理预算（reasoning budget）耗尽 —— 次可能（~15%）

如果当前模型是推理型模型（o 系列 / DeepSeek-R 系列 / Claude extended thinking 这类），「思考」和「正文」**共用同一个输出预算**。被截的内容本身就是**思考过程**（"But wait…" 是内心的自我纠错），说明它把大量 token 花在思考上，正文还没展开就烧光了。本质上是 ① 的一个子类，但值得单独列出来，因为**推理模型的思考量是隐式的、控制不了**，比普通模型更容易「半路没电」。

### ③ 上下文窗口（输入 token）满了 —— 可能性低（~3%）

- 上下文满**通常会有显式报错**（"context length exceeded" / "token limit reached"），而不是安安静静停在半句。
- 当时的输入量并不大（几个设计文档 + 一段代码），远没到窗口上限的量级。
- 所以这个基本可以排除。

### ④ 单条消息 / 工具结果长度、或超时 —— 可能性极低（~2%）

超时更可能表现为「请求超时」报错；工具结果长度限制会报「output saved to file」。都不是「干净地停在半句」的样子。

---

## 所有上限，大致数值（供建立概念）

> ⚠️ 重要：下面数字是**公开模型卡的典型值**，**无法从对话内部看到当前这个会话究竟用的是哪个模型、精确配了多少**。所以数值请当「数量级参考」，别当精确承诺。机制是确定的，具体数字因模型/配置而异。

| 上限 | 作用 | 典型数量级 | 撞上的表现 |
| --- | --- | --- | --- |
| **最大输出 token**（max output / max_completion_tokens） | 单次回复能生成多少字 | 普通 4K–16K；长输出模型 32K–128K | **停半句、无报错** |
| **思考预算**（reasoning budget） | 推理模型「思考」能烧多少 token，和正文共用输出 | 低/中/高挡位，高可到几万 token | 思考到一半戛然而止 |
| **上下文窗口**（context window） | 单次对话能塞进多少输入（历史+文档） | 128K（GPT-4o）/ 200K（Claude）/ 1M–2M（Gemini） | 通常**显式报错** "context exceeded" |
| **单条工具结果长度** | 一次 read/grep 返回的上限 | 约 20KB 文本（超了转存临时文件） | 提示 "saved to temporary file" |
| **单次请求超时** | 生成耗时上限 | 几分钟量级 | 报超时错，不是半句停 |

**关键认知**：问题**不在「存不下」，而在「单次吐不完」**。上下文（输入）再大也解决不了它，只有**把单次要产出的东西变小**才有效——这正是拆 steps 的意义。

---

## 怎么反推确认是哪一个

| 信号 | 结论 |
| --- | --- |
| 停半句、无报错、无省略号 | 输出 token / 思考预算（① ②） |
| 显式 "context length exceeded" | 上下文满（③） |
| 提示 "saved to temporary file" | 工具结果超长 |
| 一直转圈后报超时 | 超时 |

## 和正在做的事的关系

被截的内容恰好是 `design/08_testing_strategy.md` 里「Fixture 约定」那节要落地的东西——`tmp_config` / `fake_llm_provider` / `fake_request_fn_factory` 三个 fixture。模型正是在「要不要一次写三个 + 纠结 scope」这个点上把输出烧光的。

所以拆出的 `steps/step01.md` 里**明确只让它写 `tmp_config` 一个**，另外两个推到 step03/step09，就是冲着「每次产出量小」去的。这比单纯加大上限更稳，因为：

1. 没法从对话里改上限；
2. 就算能改，一次吐太多还是容易断。

## 附：另一种报错 —— `400 Invalid assistant message`

### 错误原文

```
Reason: Failed to get response from the AI model; retried 5 times (total retry wait time: 15.32 seconds)
Last error: 502 OAI Compatible API error: [400] Bad Request
{"error":{"message":"Invalid assistant message: content or tool_calls must be set",
"type":"invalid_request_error","param":null,"code":"invalid_request_error"}}
URL: https://api.deepseek.com/chat/completions
```

### 这个错误是什么（不是撞上限，是「坏消息」）

核心信息全在最后那句：`Invalid assistant message: content or tool_calls must be set`。

意思是：**发送给模型的历史消息里，有一条 assistant（助手）消息既没有 `content`（正文），也没有 `tool_calls`（工具调用）**。DeepSeek 的 API 规定 assistant 消息必须二选一有内容，否则直接 400 拒收。

### 它和刚才截断的关系（关键）

这个报错**反过来证实了之前的判断**，而且暴露了模型身份：

1. URL 是 `api.deepseek.com` → 当前用的是 **DeepSeek**，且是推理型模型（deepseek-reasoner / R1 这类）。
2. DeepSeek 推理模型把一次回复拆成两个字段：
   - `reasoning_content` —— 思考过程（"But wait…" 那段）
   - `content` —— 最终正文
3. 当思考预算烧光、生成停在半句时，它**只产出了 `reasoning_content`，没来得及产出 `content`，也没有 tool_calls**。
4. SDK 重试时，把这条「只有思考、没有正文、没有工具调用」的 assistant 消息原样塞回历史 → DeepSeek 判定它为非法消息 → 400。

所以这条 400 **不是新的独立故障，而是「截断」的下游后果**：先截断 → 留下一条空 assistant 消息 → 重试时被 API 拒收。

### 两个错误的关系一句话总结

| | 截断（上次） | 400 报错（这次） |
| --- | --- | --- |
| 本质 | 模型自己吐到一半没电了 | API 服务端拒收一条「坏消息」 |
| 发生位置 | 生成过程中（软停） | 生成开始前（硬拒） |
| 因果关系 | 原因 | 结果（重试时暴露） |

### 那些数字是什么

- `retried 5 times` / `15.32 seconds`：SDK 的自动重试机制——失败后按退避策略连试 5 次，每次重发同样（含坏消息）的历史，每次都被 400 打回，累计等了 15.32 秒后放弃。
- `502 OAI Compatible API error`：外层包装的「兼容层」状态码，真正的底层错误是里面的 `[400] Bad Request`。别被 502 误导，**根因是 400**。
- `Client Request Id:` 空：请求在还没形成完整请求 ID 前就失败了。

### 怎么办

1. **这条会话的当前 turn 已废**：那条空 assistant 消息卡在历史里，重试也救不回来。换新消息重发，或开新 turn。
2. **治本还是那句**：别让思考烧满整个预算 → 把单次任务切小（`steps/` 就是干这个的）。
3. **如果频繁出现**：属于「推理模型 + 工具调用」下 SDK/服务端的已知边界问题——客户端重发前应丢弃「空 assistant 消息」；这是客户端行为，用户侧能做的就是减小单次产出量 + 重发。

## 当前模型的确切上限（DeepSeek 官方数据，已核实）

> 这一节**修正**上文「所有上限，大致数值」里的通用典型值——那些是泛泛的公开参考，不是本会话模型的真实数字。

### 模型身份如何确认

上次 400 报错里的 URL `https://api.deepseek.com/chat/completions` 直接暴露了后端是 **DeepSeek**。结合 DeepSeek 官方文档，当前 DeepSeek API 对外只有两个模型：

| 参数 | deepseek-flash | deepseek-v4-pro |
| --- | --- | --- |
| 模型版本 | DeepSeek-V4.1-Flash-1017 | DeepSeek-V4-Pro-0813 |
| 上下文长度（context length） | **1M** | **1M** |
| 最大输出（max output） | **384K（上限）** | **384K（上限）** |
| 思考模式（thinking） | 支持，**默认开启** | 支持，**默认开启** |
| 默认思考强度（effort） | high | high |
| 工具调用（tool calls） | ✓ | ✓ |
| 视觉（vision） | ✓ | ✗ |

### 关键结论（修正上文的「典型值」）

1. **上下文不是 128K/200K，而是 1M** → 更不可能是「上下文满了」；1M 窗口塞进几个设计文档绰绰有余。
2. **输出 API 硬上限是 384K，非常高** → 说明截断**不是 API 硬上限太低**，而是**本会话（Copilot SDK）给单次请求配置的 `max_tokens` / 思考预算，远低于 384K**。这个配置值从对话内部看不到，但「会截断」这件事本身就证明有效上限被 SDK 压得很低。
3. **思考模式默认开启、默认 effort=high** → 每次回复都在烧 `reasoning_content`（思考），它和正文共用输出预算，所以「思考到一半没电」的概率被放大。

### 三个上限的准确数字

| 上限 | 准确值 | 来源 |
| --- | --- | --- |
| 上下文窗口 | **1M token** | DeepSeek 官方文档 |
| 最大输出（API 硬上限） | **384K token** | DeepSeek 官方文档 |
| 单次回复有效输出（SDK 层） | **未知，实测远低于 384K** | 本会话不可见 |

### 对上文 400 报错的补充（来自 thinking_mode 文档）

官方文档明确：思考模式下，一次回复 = `reasoning_content`（思考）+ `content`（最终答案）两个字段。**`reasoning_content` 不算「有效内容」**——DeepSeek 要求 assistant 消息必须带 `content` 或 `tool_calls` 之一。

所以 400 的精确链条是：

1. 思考预算耗尽 → 只产出 `reasoning_content`，`content` 为空、且无 `tool_calls`。
2. SDK 重试时，把这条「只有 reasoning_content」的消息塞回历史。
3. DeepSeek 判定：assistant 消息缺 `content` 又缺 `tool_calls` → 400 拒收。

这也把之前「~80% 输出上限 + ~15% 思考预算」的两个判断统一了：在 DeepSeek 这里它们本质是同一件事——**思考（`reasoning_content`）把输出预算烧光，正文（`content`）没来得及生成**。
